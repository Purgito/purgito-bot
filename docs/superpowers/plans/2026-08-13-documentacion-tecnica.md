# Documentación técnica `/es/documentacion` — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the dead `/es/docs` link with a real technical-documentation section (`/es/documentacion`) covering architecture, Discord layer, API, generation engine, storage, security (conceptual), and infrastructure — built entirely from verified facts about the actual codebase, using the site's existing static-generation pattern.

**Architecture:** Ten new pages, one per top-level category, authored as raw HTML bodies (same mechanism as `/es/perfil`, `/es/dashboard` — `HTML_PAGES` in `landing/build_docs.py`, **not** the Markdown pipeline, which can't do tables/code blocks). A new shared sidebar (generated from one Python data list, `DOC_SECTIONS`) gives every page the category nav + the current page's own subsection anchors — no JS, pure build-time HTML + a `<details>` fallback on mobile. `/es/docs` becomes a real static redirect page committed at `landing/es/docs/index.html` (nginx's existing `try_files $uri $uri/index.html` picks it up automatically — no production nginx change needed).

**Tech Stack:** Python stdlib only (`landing/build_docs.py`, already zero-dependency), plain HTML/CSS (`landing/style.css`), zero new JS.

## Global Constraints

- **No invented content.** Every factual claim in every page must trace to a real file:line in this repo (citations are listed per task below for the implementer's own verification — they are NOT published on the page).
- **Spanish only, tuteo neutro** — "elige"/"tienes"/"puedes", never "elegí"/"tenés"/"podés". No voseo, no regionalisms. (English `/en/documentation` is explicitly out of scope: `landing/index.html:34` sets `READY_LANGS = ['es']`, `landing/en/` does not exist — building it would mean standing up a whole English site first.)
- **Voice rules from CLAUDE.md "Voz y copy" apply to every string written**: no self-justification, no narrating internal state, no onboarding-assistant openers ("te guío por...", "aquí tienes..."), no redundant filler, no hedging ("podría ser que...").
- **Security & Infrastructure pages are conceptual only**: no exact rate-limit numbers, cooldown durations, or thresholds. No wording that implies "protected against X" in a way that hints what the recent security audit fixed. Describe mechanisms ("rate limiting exists, per user and per IP") never magnitudes.
- **No new dependencies.** `build_docs.py` stays stdlib-only; no markdown library, no template engine, no JS framework.
- **Do not touch nginx in production.** No changes to `/etc/nginx/conf.d/purgito.conf` on the droplet. The `/es/docs` redirect must work via the static file mechanism nginx already has (`try_files`), not via a new nginx directive.
- **Do not touch the "zonas protegidas" of `src/webapi.py`** (`_webhook_polar`, `_POLAR_*`, `_api_health`, `_api_premium_get`/`_api_premium_checkout`, `start_web_server`/`stop_web_server`) — this plan only reads from that file for documentation content, never edits it.
- **Run after every task that touches `landing/`:** `.venv/bin/python landing/build_docs.py` (writes) then `.venv/bin/python landing/build_docs.py --check` (verifies idempotence — must print `ok` and exit 0 with no diffs).
- **Run before considering the plan done:** `.venv/bin/python -m pytest tests -q`, `ruff check .`, `ruff format --check .`, `node landing/test_lang.mjs`.

def doc_sidebar(current_slug):
    """Sidebar de /es/documentacion: categorías + anclas de la página activa.

    Sin JS: la categoría activa se resuelve en build time (cada página sabe
    su propio slug) y las anclas son <a href="#id"> normales.
    """
    items = []
    for sec in DOC_SECTIONS:
        active = sec["slug"] == current_slug
        cls = ' class="active"' if active else ""
        href = "/es/%s" % sec["slug"]
        items.append('    <li%s><a href="%s">%s</a>' % (cls, href, html.escape(sec["label"])))
        if active and sec["subs"]:
            sub_items = "".join(
                '<li><a href="#%s">%s</a></li>' % (anchor, html.escape(label))
                for anchor, label in sec["subs"]
            )
            items.append('      <ul class="docs-subnav">%s</ul>' % sub_items)
        items.append("    </li>")
    return (
        '<nav class="docs-sidebar" aria-label="Documentación técnica">\n'
        '  <ul>\n%s\n  </ul>\n</nav>' % "\n".join(items)
    )

- [ ] **Step 2: Extend `build_html_page()`** (`landing/build_docs.py:351-375`) to wrap the body with the sidebar when `page.get("doc")` is set. Replace the `return SHELL.format(...)` at the end of the function:

```python
def build_html_page(page, nav, footer):
    """Página con cuerpo escrito a mano (landing/pages/*.html).

    Solo aporta el navbar, el footer y el <head> — el resto sale del archivo
    tal cual. Existe para que esas piezas no se dupliquen fuera de index.html.
    Las que traen "app" suman además dash.css y su módulo de entrada; las que
    traen "module" suman el módulo pero NO dash.css (páginas públicas con su
    propio JS, ej. /es/estado, que no son parte del dashboard). Las que traen
    "doc" son de /es/documentacion: se envuelven en el sidebar de doc_sidebar().
    """
    entry = page.get("app") or page.get("module")
    if page.get("app"):
        head = APP_HEAD.format(importmap=import_map())
    elif page.get("module"):
        head = MODULE_HEAD.format(importmap=import_map())
    else:
        head = ""
    raw_body = (LANDING / "pages" / page["src"]).read_text("utf-8").strip()
    if page.get("doc"):
        raw_body = (
            '<div class="docs-shell wrap">\n%s\n'
            '  <main id="contenido" class="docs-content">\n%s\n  </main>\n</div>'
            % (doc_sidebar(page["slug"]), raw_body)
        )
    return SHELL.format(
        title=html.escape(page["title"]),
        meta=html.escape(page["meta"]),
        nav=nav,
        body=raw_body,
        footer=footer,
        head=head,
        scripts=APP_SCRIPT.format(src=entry, v=js_files()[0]) if entry else "",
    )
```

Note: this removes the old bare `id="contenido"` from any non-doc page's own body — check that `premium.html`/`perfil.html`/`dashboard.html`/`estado.html` already define their own `#contenido` internally (they do, per the existing skip-link pattern) so this change only affects `"doc": True` pages, which don't have `#contenido` in their raw body (added by this wrapper instead).

```html
<h1>Generation Engine</h1>
<p>Purgito no usa un LLM: genera texto con una cadena de Markov de primer
orden, propia y sin dependencias externas, entrenada con el corpus de
mensajes reales de cada servidor.</p>

<h2 id="motor-markov">Markov Engine</h2>
<p>El modelo enlaza cada palabra con las que la siguieron en el corpus de
entrenamiento y arma una respuesta caminando esa cadena palabra por
palabra desde un estado inicial hasta un estado final, con un tope de
longitud y reintentos si el resultado sale demasiado corto. Sin librerías
externas de terceros — es una implementación propia deliberadamente
simple.</p>

<h2 id="corpus">Corpus</h2>
<p>Cada servidor tiene su propio corpus: los mensajes que aprende se
guardan tal cual (limpiados de menciones, URLs y IDs) en SQLite. El modelo
de un servidor se entrena con una muestra aleatoria de su corpus completo
— no está limitado al canal donde se generó el mensaje — y requiere un
mínimo de mensajes guardados antes de poder generar nada; por debajo de
ese mínimo, Purgito lo dice en vez de fallar en silencio.</p>
<p>Qué canales alimentan el corpus lo decide una lista de permitidos
propia: vacía significa que el bot no aprende de ningún canal todavía —
aprender es más invasivo que responder, así que el default seguro es no
aprender. Un canal separado, de "silenciados", corta corpus, reacciones y
triggers a la vez, independientemente de la lista de permitidos.</p>
<p>Hay también un modelo por usuario, entrenado solo con los mensajes de
esa persona, usado por los comandos que imitan a alguien en particular.</p>

<h2 id="pipeline">Generation Pipeline</h2>
<ol>
  <li>Llega un mensaje; se descarta si es de un bot o ya se procesó (guarda
  contra reintentos del gateway).</li>
  <li>Se resuelven los ajustes efectivos del canal.</li>
  <li>Si corresponde, el mensaje se limpia y se guarda en el corpus.</li>
  <li>Se evalúan triggers configurados a mano; si uno matchea, corta ahí.</li>
  <li>Si el mensaje menciona o responde al bot, o si toca una generación
  espontánea según la cadencia configurada, se arma la respuesta: primero
  se evalúa si toca una "frase especial" (contenido fijo, no generado) y
  si no, se cae a Markov.</li>
  <li>La respuesta se post-procesa — minúsculas, se sacan emojis y
  conectores finales sueltos ("y", "o", "pero"...) — y se corta si excede
  el límite de longitud de Discord antes de enviarse.</li>
</ol>

<h2 id="concurrencia-y-limites">Concurrency &amp; Limits</h2>
<p>Un semáforo global limita cuántas generaciones/entrenamientos de Markov
corren en simultáneo en todo el proceso — no es por servidor, es un tope
compartido para no saturar el pool de hilos. Los mensajes espontáneos usan
un modo no bloqueante (si no hay lugar, se saltea esa generación en vez de
esperar); las respuestas a menciones sí esperan su turno. Las escrituras a
SQLite comparten un único lock de proceso — no hay lock por servidor — así
que la separación entre servidores la da el esquema (todo indexado por
<code>guild_id</code>), no la concurrencia.</p>
<p>El corpus tiene topes de tamaño por canal, por usuario y por servidor
completo (con un plan gratuito y uno premium). Al superarse, se recorta lo
más viejo primero; el tope de servidor completo reparte el espacio
proporcionalmente entre canales en vez de vaciar uno solo. El recorte no
corre en cada mensaje — se dispara cada cierta cantidad de inserciones,
como tarea de fondo.</p>
```
