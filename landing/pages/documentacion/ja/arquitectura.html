アーキテクチャ

Purgitoは、単一のPythonプロセスと組み込みのSQLiteリレーショナルデータベースに集約される3層構成の分散システムとして設計されています:Discordボット(discord.py)、非同期のJSON API(aiohttp)、そしてnginxが配信する最適化された静的なウェブサイトです。

概要

ボットはsystemdが管理するPython 3.11+の単一プロセスとして動作します。Discordのゲートウェイとの永続的なWebSocket接続を維持し、マルコフ連鎖の生成エンジンを実行し、data/bot.dbへの読み書きを処理します。

同じイベントループ(asyncioイベントループ)内で、aiohttpのウェブサーバー(src/webapi.py)が起動し、127.0.0.1:WEB_PORT(ローカルポート)でのみ待ち受ける純粋なJSONのREST APIを公開します。このAPIはHTMLをレンダリングすることも、静的アセットを直接配信することも一切ありません。

nginxはホスト上でリバースプロキシとして機能します:動的なリクエスト(/auth/*、/api/*、/webhooks/*、/health)をPythonのローカルソケットへ振り分け、それ以外のランディングページ、ダッシュボード、ドキュメントはファイルシステムから静的ファイルとして、不変(immutable)なキャッシュヘッダーを付けて直接配信します。

システムコンポーネント

1. Discordボットとcog

Discordクライアントは専門化されたcogにモジュール化されています。各cogはスラッシュコマンド、イベントリスナー、バックグラウンドタスクをカプセル化しています。これらはsrc/bot.pyでのボット初期化時に決まった順序で読み込まれます。詳しくはDiscordを参照してください。

2. 確率的生成エンジン

1次・2次マルコフ連鎖の独自実装です。サーバーの過去のコーパスのサンプルからメモリ上に統計モデルを構築し、非同期セマフォによってグローバルな並行処理を制御します。詳しくは生成を参照してください。

3. SQLiteストレージ層

外部キー制約を有効にしたWALモード(Write-Ahead Logging)で動作する単一のリレーショナルデータベース(data/bot.db)です。サーバーごとの設定、メッセージコーパス、GIFカタログ、監査ログ、セッション情報を一元管理します。詳しくはストレージを参照してください。

4. Web APIとダッシュボードSPA

HttpOnly属性のCookieに対してFernetで暗号化したセッションを使う、ステートレスなaiohttpベースのREST APIです。管理系のルートはすべて、Discordの公式エンドポイントに対してリアルタイムで権限を検証します。ダッシュボードは、トランスパイラやパッケージングの依存を持たない、モダンなネイティブJavaScript(ESモジュール)で構築されたシングルページアプリケーションです。詳しくはAPIを参照してください。

エンドツーエンドのデータフロー

Discordメッセージのライフサイクル

  1. Discordがゲートウェイの WebSocket 経由でMESSAGE_CREATEイベントを発行します。
  2. cogs/chat.pyがon_messageでこのイベントを受け取り、ボットのメッセージや許可されていないチャンネルを除外し、そのチャンネルの実効設定を解決します。
  3. そのチャンネルで学習が許可されている場合、テキストがクリーニング(メンション、URL、特殊文字の除去)され、src/db.py経由でcorpusテーブルに永続化されます。
  4. トリガーが発火するか、応答条件(直接のメンションまたは自発的な確率)が満たされると、生成用のセマフォに順番待ちのリクエストが送られます。
  5. マルコフエンジンがメモリ上にキャッシュされたモデルを学習・再利用し、応答を生成し、フォーマットのフィルターを適用して、DiscordのREST API経由でチャンネルにメッセージを送信します。

ダッシュボードへのリクエストのライフサイクル

  1. ブラウザがダッシュボードのビュー(例:/ja/dashboard/123456/chat)をリクエストします。nginxはディスクから静的なHTMLシェルとスクリプトを即座に返します。
  2. フロントエンドが暗号化されたセッションCookieを添えて、APIへの認証済み非同期リクエスト(例:GET /api/server/123456/chat)を実行します。
  3. src/webapi.pyのミドルウェアがセッションを復号し、revoked_sessionsテーブルに含まれていないことを確認したうえで、ユーザーがサーバー123456でADMINISTRATORまたはMANAGE_GUILDの権限を持っているかをDiscordのAPIに問い合わせます。
  4. 認可が確認されると、そのエンドポイントはSQLiteでクエリを実行し、クライアント側のDOMでリアクティブに描画するための構造化されたJSONペイロードを返します。
