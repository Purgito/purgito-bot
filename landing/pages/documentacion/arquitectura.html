Arquitectura

Purgito está diseñado como un sistema distribuido en tres capas que convergen en un único proceso en Python y una base de datos relacional SQLite embebida: el bot de Discord (discord.py), una API JSON asíncrona (aiohttp) y un sitio web estático optimizado servido por nginx.

Visión general

El bot corre como un proceso único en Python 3.11+ gestionado por systemd. Mantiene la conexión WebSocket persistente con el Gateway de Discord, ejecuta el motor de cadenas de Markov y procesa operaciones de lectura y escritura sobre data/bot.db.

Dentro del mismo bucle de eventos (asyncio event loop), se inicializa un servidor web aiohttp (src/webapi.py) que expone una API REST exclusivamente en JSON escuchando en 127.0.0.1:WEB_PORT (puerto local). Esta API nunca renderiza HTML ni sirve activos estáticos directamente.

Nginx actúa como proxy inverso en el host: despacha las peticiones dinámicas (/auth/*, /api/*, /webhooks/* y /health) hacia el socket local de Python, mientras que entrega la landing page, el dashboard y la documentación directamente desde el sistema de archivos como ficheros estáticos con cabeceras de caché inmutable.

Componentes del sistema

1. Bot de Discord y cogs

El cliente de Discord está modularizado en cogs especializados. Cada cog encapsula comandos de barra diagonal (slash commands), oyentes de eventos y tareas en segundo plano. Se cargan ordenadamente al inicializar el bot en src/bot.py. Ver Discord.

2. Motor de generación probabilística

Implementación propia de cadenas de Markov de primer y segundo orden. Construye modelos estadísticos en memoria a partir de muestras del corpus histórico del servidor, controlando la concurrencia global mediante semáforos asíncronos. Ver Generación.

3. Capa de almacenamiento SQLite

Base de datos relacional única (data/bot.db) configurada en modo WAL (Write-Ahead Logging) con claves foráneas activas. Centraliza configuraciones de servidores, corpus de mensajes, catálogos de GIFs, registros de auditoría y sesiones. Ver Almacenamiento.

4. API Web y Dashboard SPA

API REST stateless en aiohttp con sesiones cifradas mediante Fernet en cookies HttpOnly. Todas las rutas administrativas verifican permisos en tiempo real contra los endpoints oficiales de Discord. El dashboard es una Single Page Application construida con JavaScript moderno modular nativo (ES Modules), sin transpiladores ni dependencias de empaquetado. Ver API.

Flujo de datos de extremo a extremo

Ciclo de un mensaje en Discord

  1. Discord emite un evento MESSAGE_CREATE por el WebSocket del Gateway.
  2. cogs/chat.py recibe el evento en on_message, descarta mensajes de bots o canales no autorizados y resuelve la configuración efectiva del canal.
  3. Si el canal tiene permitido el aprendizaje, el texto se limpia (eliminando menciones, URLs y caracteres especiales) y se persiste en la tabla corpus mediante src/db.py.
  4. Si se activa un trigger o se cumplen las condiciones de respuesta (mención directa o probabilidad espontánea), se solicita un turno al semáforo de generación.
  5. El motor de Markov entrena o reutiliza el modelo cacheado en memoria, genera la respuesta, aplica filtros de formato y envía el mensaje de vuelta al canal mediante la API REST de Discord.

Ciclo de una petición al Dashboard

  1. El navegador solicita una vista en el dashboard (ej. /es/dashboard/123456/chat). Nginx entrega inmediatamente el shell HTML y los scripts estáticos desde disco.
  2. El frontend realiza una petición asíncrona autenticada a la API (ej. GET /api/server/123456/chat) enviando la cookie de sesión cifrada.
  3. El middleware de src/webapi.py descifra la sesión, comprueba que no esté en la tabla revoked_sessions y consulta a la API de Discord si el usuario posee el permiso ADMINISTRATOR o MANAGE_GUILD en el servidor 123456.
  4. Con la autorización confirmada, el endpoint ejecuta la consulta en SQLite y retorna un payload JSON estructurado para su renderizado reactivo en el DOM del cliente.
