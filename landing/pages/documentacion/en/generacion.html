Generation engine

For chat conversation and replies, Purgito doesn't use an LLM: it generates text with a first-order Markov chain, built in-house with no external dependencies, trained on the real message corpus of each server (for the meme-caption feature, there's an optional vision integration with Groq that falls back to Markov if it's unavailable).

Markov engine

The model links each word to the ones that followed it in the training corpus, and builds a response by walking that chain word by word from a start state to an end state, with a length cap and retries if the result comes out too short. No third-party libraries — it's a deliberately simple, in-house implementation.

Corpus

Every server has its own corpus: the messages it learns are saved as-is (stripped of mentions, URLs, and IDs) in SQLite. A server's model is trained on a random sample of its full corpus — it isn't limited to the channel where the message originated — and requires a minimum number of stored messages before it can generate anything; below that minimum, Purgito says so instead of silently failing.

Which channels feed the corpus is decided by its own allowed list: empty means the bot doesn't learn from any channel yet — learning is more invasive than replying, so the safe default is not to learn. A separate "muted" channel list cuts corpus, reactions, and triggers all at once, independently of the allowed list.

There's also a per-user model, trained only on that person's messages, used by the commands that impersonate a specific user.

Generation pipeline

  1. A message arrives; it's discarded if it's from a bot or was already processed (a guard against gateway retries).
  2. The channel's effective settings are resolved.
  3. If applicable, the message is cleaned and saved to the corpus.
  4. Manually configured triggers are evaluated; if one matches, it stops there.
  5. If the message mentions or replies to the bot, or it's time for a spontaneous reply per the configured cadence, the response is built: first it checks whether a "special phrase" (fixed, not generated) applies, and if not, it falls back to Markov.
  6. The response is post-processed — lowercased, emojis and trailing loose connectors ("and", "or", "but"...) are stripped — and trimmed if it exceeds Discord's length limit before sending.

Concurrency and limits

A global semaphore limits how many Markov generations/training runs run at once across the whole process — it's not per server, it's a shared cap so the thread pool doesn't get saturated. Spontaneous messages use a non-blocking mode (if there's no room, that generation is skipped instead of waiting); replies to mentions do wait their turn. SQLite writes share a single process-wide lock — there's no per-server lock — so separation between servers comes from the schema (everything indexed by guild_id), not from concurrency.

The corpus has size caps per channel, per user, and per whole server (with a free-plan and a Premium value). Once exceeded, the oldest is trimmed first; the whole-server cap distributes the space proportionally across channels instead of emptying just one. Trimming doesn't run on every message — it fires every so many inserts, as a background task.
