Architecture

Purgito is designed as a three-tier system converging on a single Python process and an embedded SQLite relational database: the Discord bot (discord.py), an asynchronous JSON API (aiohttp), and an optimized static frontend served by nginx.

Overview

The bot runs as a single Python 3.11+ process managed by systemd. It maintains a persistent WebSocket connection to the Discord Gateway, executes the Markov chain generation engine, and performs read/write operations against data/bot.db.

Within the same asyncio event loop, an aiohttp web server (src/webapi.py) is spawned, exposing a pure JSON REST API bound strictly to 127.0.0.1:WEB_PORT (local loopback). This API never renders HTML nor serves static assets directly.

Nginx acts as the host reverse proxy: it forwards dynamic requests (/auth/*, /api/*, /webhooks/*, and /health) to the local Python socket, while serving the landing page, dashboard, and documentation directly from the filesystem as static files with immutable caching headers.

System Components

1. Discord Bot and Cogs

The Discord client is organized into specialized cogs. Each cog encapsulates slash commands, event listeners, and background tasks. They are loaded in strict order during bot initialization in src/bot.py. See Discord.

2. Probabilistic Generation Engine

A custom first- and second-order Markov chain engine. It compiles statistical models in memory from random samples of the server's corpus, managing global concurrency via asynchronous semaphores. See Generation.

3. SQLite Storage Layer

A unified relational database (data/bot.db) running in WAL mode (Write-Ahead Logging) with foreign keys enabled. It stores server configurations, message corpus, GIF catalogs, audit logs, and session revocations. See Storage.

4. Web API and SPA Dashboard

A stateless REST API built on aiohttp using Fernet-encrypted cookies marked HttpOnly. All administrative routes re-validate user permissions in real time against official Discord endpoints. The dashboard is a Single Page Application built with modern native JavaScript (ES Modules) without bundlers or compilers. See API.

End-to-End Data Flow

Discord Message Lifecycle

  1. Discord emits a MESSAGE_CREATE event across the Gateway WebSocket.
  2. cogs/chat.py receives the event in on_message, filters out bots and unauthorized channels, and computes the channel's effective configuration.
  3. If the channel is enabled for learning, text is cleaned (removing mentions, URLs, and markdown artifacts) and saved to the corpus table via src/db.py.
  4. If a trigger matches or response criteria are met (direct mention or spontaneous probability), an acquisition request is sent to the global generation semaphore.
  5. The Markov engine trains or retrieves the cached in-memory model, generates the response, applies formatting filters, and posts the message via Discord's REST API.

Dashboard Request Lifecycle

  1. The browser navigates to a dashboard view (e.g., /en/dashboard/123456/chat). Nginx immediately delivers the static HTML shell and ES modules from disk.
  2. The frontend issues an authenticated asynchronous fetch to the API (e.g., GET /api/server/123456/chat) sending the encrypted session cookie.
  3. Middleware in src/webapi.py decrypts the session, verifies it is absent from the revoked_sessions table, and queries Discord's API to confirm the user possesses ADMINISTRATOR or MANAGE_GUILD on guild 123456.
  4. With authorization confirmed, the endpoint executes SQLite queries and returns a JSON payload for reactive client-side rendering.
