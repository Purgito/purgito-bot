Architecture

Purgito is three pieces sharing a single SQLite database: the Discord bot, a JSON API in aiohttp, and a static site that serves both the public landing page and the dashboard.

Overview

The bot (Python + discord.py) is the main process: it keeps the connection to the Discord gateway, runs the text generation engine, and reads/writes directly to data/bot.db. Inside the same process runs an aiohttp server (src/webapi.py) that exposes a pure JSON API — it doesn't render HTML — listening only on 127.0.0.1; nginx is the only thing that talks to it from outside. The dashboard and the rest of the site are plain HTML/CSS/JS with no build step, served directly by nginx from the repo checkout, never touching the Python process except when they call the API.

External services: Discord (gateway + OAuth2), Cloudflare R2 (optional, stores GIFs and images if configured), Polar (Premium payments via webhook), and Cloudflare as the CDN/proxy layer in front of nginx.

Components

Bot and cogs

The bot is built as a collection of discord.py cogs, each responsible for one area: chat/Markov, gifs, memes, youtube, scheduled announcements, premium, general settings, the settings panel, and the embed editor's layout buttons. See Discord.

Generation engine

Builds and caches a Markov model per server from the saved corpus, with a global limit on concurrent generation/training tasks. See Generation engine.

SQLite

A single database (data/bot.db) for configuration, corpus, GIFs, sessions, and everything else — no external engine. See Storage.

API + Dashboard

The JSON API authenticates by session (encrypted cookie) and authorizes every call by checking live, against Discord's own API, that whoever is calling administers the server they're asking about. The dashboard is plain JS that consumes that API. See API.

Request flow

A Discord message

  1. The gateway delivers the on_message event.
  2. The channel's effective settings are resolved (overrides on top of the server's).
  3. If the channel is enabled for learning, the message is saved to the corpus.
  4. Configured triggers are evaluated, and if the message mentions or replies to the bot, or it's time for a spontaneous reply, it's handed off to the generation engine.
  5. The engine builds (or reuses from cache) the server's Markov model, generates a response, and post-processes it.
  6. The bot sends the response.

A dashboard request

  1. The browser sends the session cookie (encrypted, with no server-side state beyond a revocation list).
  2. Every server-specific endpoint verifies, against Discord's own API and never against anything the client sends, that the session administers that server.
  3. The handler reads or writes to SQLite and returns JSON — never HTML.
