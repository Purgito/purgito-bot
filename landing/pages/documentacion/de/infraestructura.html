Infrastruktur

Purgito läuft auf einer optimierten Einzelknoten-Infrastruktur unter Linux: einem Nginx-Reverse-Proxy am Rand des Servers, einem asynchronen Python-Prozess, verwaltet von systemd, und dem Cloudflare-Netzwerk als CDN und perimetrische Sicherheitsschicht.

Laufzeitumgebung (Runtime)

Der Bot und seine Web-API laufen gemeinsam in einem einzigen Python-3.11+-Prozess innerhalb desselben asynchronen Ereignis-Loops (asyncio event loop):

  • Verwaltung mit systemd: Der Dienst bot-purg.service verwaltet den Lebenszyklus des Prozesses auf dem Server, übernimmt automatische Neustarts nach Abstürzen und leitet Logs an journald weiter.
  • Netzwerkisolation: Die HTTP-API (aiohttp) lauscht ausschließlich auf 127.0.0.1:WEB_PORT (standardmäßig Port 8080/8081). Kein Socket der Python-Anwendung ist direkt dem Internet ausgesetzt.

Nginx-Topologie

Nginx fungiert als einziger lokaler Einstiegspunkt und trennt den Verkehr zwischen statischen und dynamischen Inhalten:

Eingehende Anfrage (HTTPS)
           │
           ▼
     ┌───────────┐
     │   Nginx   │
     └─────┬─────┘
           │
     ┌─────┴────────────────────────────────┐
     │                                      │
     ▼ Dynamische Routen                    ▼ Statische Routen
/api/*, /auth/*, /webhooks/*, /health       /es/*, /en/*, /assets/*, /style.css
     │                                      │
     ▼ proxy_pass                           ▼ try_files
┌─────────────────────────┐           ┌─────────────────────────┐
│  Python 127.0.0.1:8080  │           │   Direkt von der Platte │
│   aiohttp REST API      │           │   (Zero Python-CPU)     │
└─────────────────────────┘           └─────────────────────────┘
  • Statische Auslieferung mit hoher Performance: Alle HTML-Seiten (Landingpage, Leitfäden, Dokumentation, Dashboard), CSS-Stile, JS-Skripte und öffentliche Bilder werden direkt aus dem Dateisystem ausgeliefert, ohne den Python-Prozess zu beanspruchen oder Speicher der Anwendung zu verbrauchen.
  • Dynamische Routen des Dashboards: Die Nginx-Regel leitet jede URL mit Server-ID (z. B. /de/dashboard/{id}/*) an die entsprechende statische Datei des Dashboards weiter, sodass die Single Page Application die Route auf dem Client auflösen kann.
  • Sicherheits- und Cache-Header: Nginx fügt Sicherheitsheader ein (CSP, X-Content-Type-Options, Referrer-Policy) und wendet Cache-Control: public, max-age=31536000, immutable auf die mit Cache-Busting-Hashes versionierten Dateien an (?v=...).

CDN- und Sicherheitsschicht (Cloudflare)

Cloudflare steht vor dem Ursprungsserver und fungiert als TLS-Proxy und Content-Delivery-Netzwerk:

  • TLS-1.3-Terminierung: Verwaltet die SSL/TLS-Zertifikate und die Verschlüsselung zum Client.
  • Caching am Edge: Speichert statische Assets (Bilder, CSS, JS) in weltweit verteilten Rechenzentren zwischen, fängt den Traffic der Landingpage ab und reduziert die Last auf dem Server.
  • DDoS-Abwehr und WAF: Filtert Denial-of-Service-Angriffe auf Netzwerk- und Transportebene, bevor sie den Port von Nginx erreichen.

Kontinuierliches Deployment ohne Build-Schritt

Die Architektur von Purgito macht aufwendige Build-Schritte (build steps) auf dem Server überflüssig:

  1. Der Quellcode, die Skripte und die von landing/build_docs.py vorgenerierten Seiten sind direkt im Git-Repository versioniert.
  2. Das Deployment besteht aus dem Synchronisieren der Änderungen mit git pull.
  3. Die Integritätsprüfung der Dokumentation wird ausgeführt: python3 landing/build_docs.py --check.
  4. Der Dienst wird mit systemctl restart bot-purg.service neu gestartet, wodurch die Aktualisierung in wenigen Sekunden abgeschlossen ist.
