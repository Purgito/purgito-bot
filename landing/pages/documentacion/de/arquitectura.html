Architektur

Purgito ist als verteiltes System in drei Schichten konzipiert, die in einem einzigen Python-Prozess und einer eingebetteten relationalen SQLite-Datenbank zusammenlaufen: dem Discord-Bot (discord.py), einer asynchronen JSON-API (aiohttp) und einer optimierten statischen Website, ausgeliefert von nginx.

Überblick

Der Bot läuft als einzelner Prozess in Python 3.11+, verwaltet von systemd. Er hält die dauerhafte WebSocket-Verbindung zum Gateway von Discord aufrecht, betreibt die Markov-Ketten-Engine und führt Lese- und Schreiboperationen auf data/bot.db aus.

Innerhalb desselben Ereignis-Loops (asyncio event loop) wird ein aiohttp-Webserver (src/webapi.py) initialisiert, der eine ausschließlich JSON-basierte REST-API bereitstellt und auf 127.0.0.1:WEB_PORT (lokaler Port) lauscht. Diese API rendert niemals HTML und liefert keine statischen Assets direkt aus.

Nginx fungiert auf dem Host als Reverse-Proxy: Er leitet dynamische Anfragen (/auth/*, /api/*, /webhooks/* und /health) an den lokalen Python-Socket weiter, während er die Landingpage, das Dashboard und die Dokumentation direkt aus dem Dateisystem als statische Dateien mit unveränderlichen Cache-Headern ausliefert.

Komponenten des Systems

1. Discord-Bot und Cogs

Der Discord-Client ist in spezialisierte Cogs modularisiert. Jeder Cog kapselt Slash-Commands, Event-Listener und Hintergrundaufgaben. Sie werden beim Initialisieren des Bots in src/bot.py in geordneter Reihenfolge geladen. Siehe Discord.

2. Engine für probabilistische Generierung

Eigene Implementierung von Markov-Ketten erster und zweiter Ordnung. Sie baut statistische Modelle im Arbeitsspeicher aus Stichproben des historischen Corpus des Servers auf und steuert die globale Nebenläufigkeit über asynchrone Semaphoren. Siehe Generierung.

3. SQLite-Speicherschicht

Einzige relationale Datenbank (data/bot.db), konfiguriert im WAL-Modus (Write-Ahead Logging) mit aktiven Fremdschlüsseln. Sie zentralisiert Serverkonfigurationen, Nachrichten-Corpus, GIF-Kataloge, Audit-Protokolle und Sitzungen. Siehe Speicher.

4. Web-API und Dashboard-SPA

Zustandslose REST-API in aiohttp mit über Fernet verschlüsselten Sitzungen in HttpOnly-Cookies. Alle administrativen Routen prüfen Berechtigungen in Echtzeit gegen die offiziellen Endpunkte von Discord. Das Dashboard ist eine Single Page Application, gebaut mit modernem, nativem modularem JavaScript (ES Modules), ohne Transpiler oder Bundling-Abhängigkeiten. Siehe API.

Datenfluss von Anfang bis Ende

Zyklus einer Nachricht auf Discord

  1. Discord sendet ein MESSAGE_CREATE-Ereignis über den WebSocket des Gateways.
  2. cogs/chat.py empfängt das Ereignis in on_message, verwirft Nachrichten von Bots oder aus nicht autorisierten Kanälen und ermittelt die effektive Konfiguration des Kanals.
  3. Ist das Lernen für den Kanal erlaubt, wird der Text bereinigt (Erwähnungen, URLs und Sonderzeichen entfernt) und über src/db.py in der Tabelle corpus gespeichert.
  4. Wird ein Trigger ausgelöst oder sind die Antwortbedingungen erfüllt (direkte Erwähnung oder spontane Wahrscheinlichkeit), wird ein Slot am Generierungs-Semaphor angefragt.
  5. Die Markov-Engine trainiert das Modell oder nutzt das im Arbeitsspeicher zwischengespeicherte, erzeugt die Antwort, wendet Formatierungsfilter an und sendet die Nachricht über die REST-API von Discord zurück an den Kanal.

Zyklus einer Anfrage an das Dashboard

  1. Der Browser ruft eine Ansicht im Dashboard auf (z. B. /de/dashboard/123456/chat). Nginx liefert sofort das HTML-Grundgerüst und die statischen Skripte von der Festplatte aus.
  2. Das Frontend stellt eine asynchrone, authentifizierte Anfrage an die API (z. B. GET /api/server/123456/chat) und sendet dabei das verschlüsselte Sitzungscookie mit.
  3. Die Middleware in src/webapi.py entschlüsselt die Sitzung, prüft, dass sie nicht in der Tabelle revoked_sessions steht, und fragt bei der API von Discord ab, ob der Nutzer die Berechtigung ADMINISTRATOR oder MANAGE_GUILD auf dem Server 123456 besitzt.
  4. Nach bestätigter Autorisierung führt der Endpunkt die Abfrage in SQLite aus und liefert ein strukturiertes JSON-Payload für die reaktive Darstellung im DOM des Clients zurück.
