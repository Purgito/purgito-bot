API

Die API von Purgito ist eine asynchrone JSON-REST-Schnittstelle, aufgebaut auf aiohttp.web. Sie läuft im selben Prozess wie der Bot auf 127.0.0.1:WEB_PORT und wird über den Reverse-Proxy von Nginx sicher ins Internet exponiert.

OAuth2-Authentifizierung und Sitzungen

Der Zugriff auf das Dashboard nutzt den Standard-OAuth2-Autorisierungsablauf von Discord (Authorization Code Flow):

  1. GET /auth/login erzeugt einen kryptographisch sicheren state-Parameter mit secrets.token_urlsafe(32) und leitet den Nutzer zur Zustimmungsseite von Discord weiter, mit den Scopes identify, email und guilds.
  2. Discord leitet zu GET /auth/callback weiter, mit dem Autorisierungscode und dem state.
  3. Der Server tauscht den Code über https://discord.com/api/v10/oauth2/token gegen ein Zugangstoken ein, ruft das Nutzerprofil sowie die von ihm verwalteten Server ab (/users/@me/guilds). Verwaltet der Nutzer keinen Server, auf dem der Bot vorhanden oder verfügbar ist, wird die Authentifizierung verweigert.
  4. Ein Sitzungscookie wird ausgestellt, symmetrisch verschlüsselt mit Fernet (SESSION_SECRET), mit den Eigenschaften HttpOnly, SameSite=Lax und Secure.

Um Sitzungen zu invalidieren, ohne einen aufwendigen Zustand im Arbeitsspeicher zu halten, speichert die Tabelle revoked_sessions die Kennungen explizit über POST /auth/logout beendeter Sitzungen. Jede eingehende Anfrage prüft, dass die Sitzungs-ID nicht in dieser Tabelle steht.

Endpunkte pro Server (/api/server/{guild_id}/*)

Alle Routen unter diesem Präfix erfordern eine aktive Sitzung und prüfen in Echtzeit, dass der Nutzer die Berechtigung Server verwalten auf dem angefragten Server besitzt:

  • GET/POST /api/server/{id}/style: Abfrage und Aktualisierung von Avatar, Spitzname und Banner von Purgito auf dem Server.
  • GET/POST /api/server/{id}/stats: Detaillierte Metriken zu Nachrichtenspeicher, GIFs, Sprüchen, historischer Aktivität und Kontingenten.
  • GET/PUT /api/server/{id}/chat: Einstellungen zur Generierung, Prozentsätze für spontane Antworten und Nachrichtenlimits.
  • GET/PUT /api/server/{id}/canales: Matrix aus Lesekanälen, Antwortkanälen, stummgeschalteten Kanälen und ignorierten Rollen.
  • GET/POST/DELETE /api/server/{id}/gifs: GIF-Katalog, Datei-Upload und einzelnes oder massenhaftes Löschen.
  • GET/POST/DELETE /api/server/{id}/memes: Vorlagen und Bilder der Meme-Bank.
  • GET/POST/DELETE /api/server/{id}/triggers: Automatische Antworten bei exakter Übereinstimmung, Präfix oder regulären Ausdrücken (Regex).
  • GET/POST/DELETE /api/server/{id}/reacciones: Regeln für automatische Emoji-Reaktionen.
  • GET/POST/DELETE /api/server/{id}/frases: Benutzerdefinierte Sprüche und thematische Pakete pro Kanal.
  • GET/POST/DELETE /api/server/{id}/embeds: Vorlagen für klassische Embeds und interaktive Layout-V2-Blöcke.
  • POST /api/server/{id}/embeds/send: Sofortiger Versand einer gestalteten Nachricht an einen Discord-Kanal.
  • GET/PUT/DELETE /api/server/{id}/events/{event_type}: Abfrage, Konfiguration (Klartext, klassisches Embed, Layout V2) und Zurücksetzen von Willkommens-, Abschieds- und Boost-Events mit Variablen-Engine.
  • POST /api/server/{id}/events/{event_type}/test: Versand einer Testnachricht mit aufgelösten dynamischen Variablen an den konfigurierten Kanal.
  • GET/POST/DELETE /api/server/{id}/anuncios: Planung und Verwaltung automatisierter Ankündigungen.
  • GET/POST/DELETE/PATCH /api/server/{id}/youtube: Abonnements und Alarmkanäle für neue Videos.
  • GET/POST/DELETE/PATCH /api/server/{id}/rss: Abonnements generischer RSS/Atom-Feeds und Alarmkanäle für neue Veröffentlichungen.
  • POST /api/server/{id}/amnesia: Leerung des in den letzten 24 Stunden gelernten Nachrichten-Corpus und Stils.
  • GET /api/server/{id}/audit: Audit-Protokoll der über das Dashboard vorgenommenen Änderungen.

Zahlungs-Webhooks (Polar)

POST /webhooks/polar empfängt von Polar ausgelöste Ereignisse zu Abonnements und Abrechnung:

  • Signaturprüfung: Der Header Webhook-Signature wird nach dem Standard Standard Webhooks (HMAC-SHA256) mit dem Secret POLAR_WEBHOOK_SECRET validiert. Ist die Signatur ungültig oder der Header nicht vorhanden, wird die Anfrage mit Code 400 abgelehnt.
  • Reihenfolge der Ereignisse: Jeder Payload enthält Zeitstempel, um zu garantieren, dass im Netzwerk verzögerte Ereignisse nicht neuere Zustände überschreiben.
  • Verarbeitete Ereignisse: subscription.created, subscription.updated, subscription.active, subscription.canceled und order.refunded, die in Echtzeit die Tabelle guild_premium aktualisieren.
