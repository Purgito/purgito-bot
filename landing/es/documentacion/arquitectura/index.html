Arquitectura

Purgito son tres piezas que comparten una única base de datos SQLite: el bot de Discord, una API JSON en aiohttp y un sitio estático que sirve tanto la landing pública como el dashboard.

Visión general

El bot (Python + discord.py) es el proceso principal: mantiene la conexión con el gateway de Discord, corre el motor de generación de texto y escribe/lee directamente sobre data/bot.db. Dentro del mismo proceso corre un servidor aiohttp (src/webapi.py) que expone una API JSON pura — no renderiza HTML — escuchando solo en 127.0.0.1; nginx es el único que le habla desde afuera. El dashboard y el resto del sitio son HTML/CSS/JS planos sin build step, servidos directamente por nginx desde el checkout del repo, sin pasar por el proceso de Python en absoluto salvo cuando llaman a la API.

Servicios externos: Discord (gateway + OAuth2), Cloudflare R2 (opcional, almacena GIFs e imágenes si está configurado), Polar (pagos de Premium vía webhook) y Cloudflare como capa de CDN/proxy delante de nginx.

Componentes

Bot & cogs

El bot se arma como una colección de cogs de discord.py, cada uno responsable de un área: chat/Markov, gifs, memes, youtube, anuncios programados, premium, ajustes generales, el panel de configuración y los botones de layout del editor de embeds. Ver Discord.

Generation Engine

Construye y cachea un modelo de Markov por servidor a partir del corpus guardado, con un límite global de tareas de generación concurrentes. Ver Generation Engine.

SQLite

Una única base de datos (data/bot.db) para configuración, corpus, GIFs, sesiones y todo lo demás — sin motor externo. Ver Storage.

API + Dashboard

La API JSON autentica por sesión (cookie cifrada) y autoriza cada llamada verificando en vivo, contra la propia API de Discord, que quien llama administra el servidor que pide. El dashboard es JS plano que consume esa API. Ver API.

Flujo de una petición

Un mensaje en Discord

  1. El gateway entrega el evento on_message.
  2. Se resuelven los ajustes efectivos del canal (overrides sobre los del servidor).
  3. Si el canal está habilitado para aprender, el mensaje se guarda en el corpus.
  4. Se evalúan triggers configurados, y si el mensaje menciona o responde al bot, o si toca generar espontáneamente, se pasa al motor de generación.
  5. El motor arma (o reutiliza del caché) el modelo de Markov del servidor, genera una respuesta y la post-procesa.
  6. El bot envía la respuesta.

Una petición al dashboard

  1. El navegador manda la cookie de sesión (cifrada, sin estado en el servidor más allá de una lista de revocación).
  2. Cada endpoint de servidor específico verifica, contra la propia API de Discord y no contra nada que mande el cliente, que la sesión administra ese servidor.
  3. El handler lee o escribe en SQLite y devuelve JSON — nunca HTML.
